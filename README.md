# Java Web CI/CD Pipeline Using Jenkins, Maven & Tomcat

## Project Overview

This project demonstrates an end-to-end Continuous Integration and Continuous Deployment (CI/CD) pipeline for a Java web application using Jenkins, Maven, Git, and Apache Tomcat.

The pipeline retrieves source code from GitHub, builds and tests the application, publishes JUnit test results, archives the WAR artifact, deploys it to Tomcat, and performs an application health check. If the health check fails, the pipeline attempts to restore a previous working WAR, restart Tomcat, and verify application recovery.

## Architecture

**Normal deployment flow**

Developer → GitHub → Jenkins → Maven Build & Unit Tests → JUnit Test Report → WAR Artifact → Tomcat Deployment → Health Check

**Rollback flow**

Health Check Failure → Restore Previous WAR → Restart Tomcat → Verify Application Recovery

## CI/CD Pipeline Stages

1. **Source Checkout:** Jenkins retrieves the source code and Jenkinsfile from GitHub.
2. **Environment Check:** Jenkins checks the installed Java and Maven versions.
3. **Build and Test:** Maven compiles the application, executes unit tests, and packages the WAR.
4. **Test Reporting:** Jenkins publishes JUnit test results.
5. **Artifact Archiving:** Jenkins archives the generated WAR and records its fingerprint.
6. **Tomcat Deployment:** Jenkins copies the WAR into Tomcat's `webapps` directory.
7. **Application Health Check:** Jenkins uses `curl -f` to verify that the application endpoint responds successfully.
8. **Automatic Rollback:** If the health-check stage fails, the pipeline attempts to restore the previous WAR, restart Tomcat, and check application recovery.

## Failure Testing and Recovery

### 1. Unit Test Failure

An assertion was intentionally changed to an incorrect expected value to simulate a test failure.

- Maven reported one failed test.
- Jenkins marked the build as failed.
- The JUnit reporting, artifact archiving, deployment, and health-check stages were skipped.
- The assertion was restored, and a subsequent build passed.

This demonstrated that the pipeline prevents deployment when unit tests fail.

### 2. Deployment Health-Check Failure

The health-check URL was temporarily changed to an invalid path to simulate a deployment verification failure.

- The initial health check returned HTTP 404.
- Jenkins executed the rollback block.
- The previous WAR was restored.
- Tomcat was restarted.
- The application returned the Version 1 page successfully after rollback.

The build remained marked as failed because the original health check intentionally failed, even though the rollback recovery check succeeded. A subsequent normal pipeline run deployed Version 2 successfully.

### 3. Git Recovery

The temporary invalid health-check URL was introduced in a dedicated commit and corrected in a later commit. Git history preserves both the failure simulation and the corrective change for review.

## Running the Project

1. Clone the repository from GitHub.
2. Configure Java, Maven, Jenkins, and Tomcat in the environment.
3. Configure the Jenkins job to use the repository and its `Jenkinsfile`.
4. Ensure Jenkins has the necessary permissions to deploy the WAR and restart Tomcat.
5. Run the Jenkins pipeline.
6. Review the console output, JUnit results, and archived WAR artifact.
7. Verify the deployed application using the configured Tomcat endpoint.
